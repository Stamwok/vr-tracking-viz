# Интринсики камеры: порядок `[cx, cy, fx, fy]` и per-eye модель SBS

> Источник чисел — `cameraIntrinsics` из header'а файла трекинга:
> `[1079.5, 404.5, 1373.6681390725917, 686.8680648828482]`.
> Реализация — `src/camera_model.py` (`Intrinsics`, `Intrinsics.from_header`,
> `Intrinsics.per_eye`), тесты — `tests/test_camera_model.py`,
> CLI — `python src/camera_model.py data/trackingData_*.txt`.

## 1. Размер кадра выводится из центра (width/height в header нет)

В header есть только `timeStampNs`, `cameraIntrinsics` и `cameraExtrinsics` — ширины/высоты
кадра нет (CLAUDE.md §3.1). Поэтому размер выводится из первых двух чисел по half-pixel
конвенции OpenCV: координаты пикселей целые, поэтому центр кадра шириной W — это
`(W − 1)/2 = W/2 − 0.5`:

- `2 · 1079.5 + 1 = 2160` — ровно ширина записанного видео (2160 px, `output/video_meta.json`);
- `2 · 404.5 + 1 = 810` — ровно его высота (810 px).

Оба числа целые и совпадают с реальным кадром 2160×810 (задача 02), значит первые два числа
массива — это `cx, cy`. В коде это проверка в `Intrinsics.from_header`: если `2·cx + 1` или
`2·cy + 1` не целое (допуск 1e-6) — `ValueError`.

## 2. Почему не `[fx, fy, cx, cy]`

Если прочитать массив как `[fx, fy, cx, cy]`, то `cx = 1373.668`:

- даёт `2 · cx + 1 = 2748.336` — не целое и на **588.34 px** больше ширины кадра 2160,
  т.е. проверка «`2·cx + 1` целое и равно ширине» отсекает такой порядок до всякой проекции;
- **выходит за пределы глаза шириной 1080 px**: 1373.668 − 1080 = **293.67 px** в правую
  половину SBS, «центр левого глаза» оказался бы в правом;
- `cy = 686.868` вместо 404.5 — это не центр кадра высотой 810 px.

Побочные признаки того же (неверного) порядка: фокусные были бы 1079.5 и 404.5 px, их
отношение 2.669 — «пиксели» растянуты в 2.67 раза; FOV одного глаза (1080×810) при этом
`2·atan(540/1079.5) = 53.15°` по горизонтали и `2·atan(405/404.5) = 90.07°` по вертикали
(диагональ `2·atan(hypot(540/1079.5, 405/404.5)) = 96.44°`) — вертикальный FOV больше
горизонтального, для камеры шлема это странно, но само по себе ещё не абсурд.

**Уточнение:** сам по себе перекос FOV такой порядок не отсекает: 53.15° на один глаз
(и `2·atan(1080/1079.5) = 90.03°` на полный кадр 2160) — подозрительно, но не более.
Порядок отсекает проверка центра/размера: `2 · 1373.668 + 1 = 2748.336 ≠ 2160`.

## 3. `fx` посчитан от полной ширины SBS-кадра

`fx = 1373.668` при полной ширине 2160 px даёт hFOV 76.350°, тот же, что у одного глаза
1080 px с фокусным 686.868 px:

`2·atan(1080/1373.668) = 76.350°`, `2·atan(540/686.868) = 76.347°`.

То есть `fx` — от полной ширины SBS-кадра (≈ 2 × 686.868), а `fy` — от его высоты (810 px,
общей для обоих глаз).

Для одного глаза пиксели квадратные — половина ширины 540 px и половина высоты 405 px при
одном фокусном:

`540 / 686.868 = 0.78618`, `405 / 686.868 = 0.58963`, отношение `0.78618 / 0.58963 = 1.3333 = 4/3`,
т.е. `540/f = 1.333 · 405/f`.

## 4. Уточнение: `fx ≠ 2·fy` ровно (расхождение 0.068 px)

Записи 27.10 (CLAUDE.md §5.1, `docs/NOTES.md`) утверждают «`1373.668 = 2 × 686.868`» — это
приближение:

- `2 × 686.8680648828482 = 1373.7361297656964`, а в файле `1373.6681390725917` — разница
  **0.0680 px (0.00495 %)**;
- `fx_full / 2 = 686.8340695362958`, а `fy = 686.8680648828482` — разница **0.0340 px
  (0.00495 %)**.

Значит одно из чисел посчитано с округлением (или `fx` снят при другой ширине): точного
равенства «`fx = 2·fy`» в данных нет, и принимать его за константу нельзя.

**Выбор:** `fx_eye = fy = 686.8680648828482` — пиксели строго квадратные, `fy` берётся из
файла без изменений. Альтернатива `fx_eye = fx_full/2 = 686.8340695362958` отличается на
0.034 px (0.005 %): hFOV 76.350° вместо 76.347° (+0.0028°), а в проекции — сдвиг меньше
**0.03 px** у края кадра (0.027 px при `X/Z = 540/f`). Это меньше 1/30 px — на наложение не
влияет, поэтому выбор зафиксирован в пользу квадратных пикселей.

## 5. per-eye модель (один глаз 1080×810)

| глаз | fx, px | fy, px | cx, px | cy, px | кадр | hFOV | vFOV | диагональ |
|---|---|---|---|---|---|---|---|---|
| левый | 686.868065 | 686.868065 | 539.5 | 404.5 | 1080×810 | 76.35° | 61.05° | 89.00° |
| правый | 686.868065 | 686.868065 | 1619.5 | 404.5 | 1080×810 | 76.35° | 61.05° | 89.00° |

- `cx` левого глаза: `1079.5 − 1080/2 = 539.5` (центр левой половины в координатах полного
  кадра). У правого глаза `cx = 539.5 + 1080 = 1619.5` — тоже в координатах полного SBS-кадра;
  при обрезке правой половины (`frame[:, 1080:]`) координаты сдвигаются на −1080, поэтому в
  обрезанном кадре `cx = 539.5`. Значение 1619.5 годится для проекции в полный кадр 2160;
- `cy = 404.5` у обоих (высота общая, 810 px);
- FOV по `2·atan(half/f)`: half_w = 540, half_h = 405,
  `h = 2·atan(540/686.868) = 76.347°`, `v = 2·atan(405/686.868) = 61.050°`,
  диагональ `2·atan(hypot(540, 405)/686.868) = 2·atan(675/686.868) = 89.001°`
  (гипотенуза ровно 675 px: 540² + 405² = 675²).

## 6. Внешнее подтверждение FOV (XRoboToolkit, SII 2026)

Статья XRoboToolkit (2026 IEEE/SICE SII, DOI 10.1109/SII64115.2026.11404528), §II-E, независимо
приводит FOV камеры PICO 4 Ultra: **«horizontal and vertical angles of approximately 76.35° and
61.05°, respectively»** (для сравнения там же: ZED Mini — 82° × 52°). Это те же углы, что даёт
наша per-eye модель 1080×810 с `fx = fy = 686.8680648828482`:

| источник | hFOV | vFOV | диагональ |
|---|---|---|---|
| per-eye интринсики (`fx = fy = 686.868`) | 76.347° | 61.050° | 89.001° |
| статья, §II-E | 76.35° | 61.05° | — |
| расхождение | 0.003° | < 0.001° | — |

Расхождение — только округление статьи до двух знаков: `76.347°` и `61.050°` дают ровно
`76.35°` и `61.05°`. Это независимое подтверждение масштаба и per-eye модели (один глаз
1080×810, половины 540×405), а не только нашей арифметики.

**Чего это подтверждение не даёт.** Статья не публикует `cameraIntrinsics` (в Table I их нет),
поэтому:

- она не доказывает порядок `[cx, cy, fx, fy]` — он по-прежнему выведен из данных (§1–2);
- при точности статьи до 0.01° она не различает `fx_eye = fy = 686.868` и альтернативу
  `fx_eye = fx_full / 2 = 686.834`: у второй hFOV = 76.350° (расхождение с `fy`-вариантом
  0.003°), обе согласуются с 76.35°; выбор в пользу `fx_eye = fy` сделан по квадратным
  пикселям (§4), а не по статье;
- вертикаль 61.05° совпадает с `2·atan(405/686.868) = 61.050°` в пределах округления и
  подтверждает `fy`, но не порядок массива.

Размер стереокадра статья подтверждает отдельно: §III-B — «2160×810 resolution stereo video
streaming» (поток в статье — 60 Гц, наша запись — 30 fps: это разные режимы, не противоречие);
раскладку side-by-side она не описывает, шов на `x = 1080` проверен по данным (README,
«Сложности» п. 4).

Итог: статья **согласуется** с per-eye моделью и подтверждает FOV PICO 4 Ultra, но интринсики
и их порядок остаются выведенными из данных.

## 7. API и допущения

```python
from src.camera_model import Intrinsics
from src.parse_tracking import read_header

path = "data/trackingData_20260505_165740.txt"     # файл записи
intr = Intrinsics.from_header(read_header(path))   # полный кадр 2160×810
intr.full_w, intr.full_h                           # 2160, 810
left = intr.per_eye("left")                        # 1080×810: fx = fy = 686.868, cx = 539.5
right = intr.per_eye("right")                      # 1080×810: cx = 1619.5 (в полном кадре)
left.fov_deg()                                     # (76.347, 61.050, 89.001)
```

- `from_header(header)` выводит размер из центра (`2·cx + 1`, `2·cy + 1`);
  `from_header(header, frame_size=(w, h))` дополнительно проверяет, что центр совпадает с
  `(w/2 − 0.5, h/2 − 0.5)` с допуском 1e-6, и что `w` чётное (SBS);
- `full_w/full_h` — размер кадра, на котором задана модель; `eye_w == full_w // 2` —
  инвариант датакласса. В per-eye модели `full_*` — это изображение глаза 1080×810, поэтому
  `eye_w` по инварианту равна 540 и в FOV/проекции не участвует.

Допущения и ограничения:

- модель — **пинхол** (прямолинейная проекция); **дисторсии в header нет**, поэтому не
  компенсируем. У камеры шлема дисторсия обычно правится драйвером до склейки SBS, но
  проверить это по имеющимся данным нечем — на краях кадра возможна остаточная ошибка;
- **SBS-шов ровно на x = 1080** (2160×810, два глаза по 1080×810; подтверждено в 02a);
- **левая половина — рабочая**, правая нужна только для проверки стерео (CLAUDE.md §7.4);
- FOV — по прямоугольнику глаза 1080×810; «квадратные пиксели» — допущение `fx_eye = fy`
  (см. §4).

## 8. Проверка

```bash
python src/camera_model.py data/trackingData_20260505_165740.txt
```

Печатает сырые 4 числа, интерпретацию `[cx, cy, fx, fy]`, полный кадр 2160×810 и таблицу
per-eye с FOV; на битом header'е или отсутствующем файле — сообщение в stderr и код 1.
Синтетический тест с порядком `[fx, fy, cx, cy]` (`tests/test_camera_model.py`) требует
`ValueError`, диагональ per-eye проверяется в пределах 88–90° (факт — 89.001°).
